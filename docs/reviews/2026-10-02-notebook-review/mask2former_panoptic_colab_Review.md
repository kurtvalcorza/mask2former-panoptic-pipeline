## Executive assessment

The default workflow is technically careful and its claims are honest. The pinned identity is carried twice and asserted
before anything is fetched; all four snapshot files are digest-verified before loading; validation runs before the model
and records one rejection; the carried module implements the upstream per-pixel void rule itself (this review confirmed
that the pinned `transformers` post-processor would hand the whole drawn frame to the one surviving query, area 1.0, as
the notebook says); scores are called uncalibrated; and the class-agnostic PQ on the drawn scene is labelled
`sample-sanity` plumbing evidence, never a benchmark. The exact blob under review has a clean-runtime Kaggle CPU record,
and a direct CPU execution in this review reproduced every recorded number (one `stop sign` 0.601 over 8.3 %, void
91.7 %, PQ 0.330; the photograph's five segments; the blank and noise probes).

Two Major problems stop it being ready. **Run all does not complete in one pass**: the same Kaggle record shows the
install cell raising its own restart guard (`numpy: loaded=2.0.2, installed=2.5.3`) and the run passed only after the
executor restarted the kernel, while `tutorials/README.md` lists Run-all as "verified". **The notebook declares `GUIDED`
but has almost none of the guided layer**: no audience statement, how-to-use, roadmap, glossary, predictions,
checkpoints with sample answers, structured experiment, troubleshooting or conclusion scaffold, and its 1,256 lines of
carried package code are neither labelled as infrastructure nor collapsed. Five Minor findings cover BYOD recovery
messages, silent BYOD input alteration (EXIF orientation, 16-bit images), an experiment list with no rerun instruction
and one stated outcome that does not occur, evidence gaps (no Colab record, BYOD never recorded), and an undocumented
environment variable.

No finding here says the recorded default-path numbers are wrong.

## 2. Separate judgments

**Technical correctness.** Strong on the default path: identity asserted twice, digest verification before load, no
remote code, validation through the same function `segment` uses, the upstream void rule implemented and its necessity
demonstrated, exports carry model revision, notebook source and runtime. Two defects: the in-kernel install cannot
complete Run all in one pass on the recorded hosted image (M2P-M1), and BYOD conversion silently alters some valid
inputs (M2P-m2).

**Promise fulfilment.** The default promises are delivered and evidenced by the exact-blob Kaggle run and by this
review's CPU run, except "Run all … needs no … intervention" (M2P-M1). The BYOD promise "passes through the same
validation, task, evaluation-report and export cells" holds for ordinary RGB images (P04), but unusable uploads fail
with raw exceptions (M2P-m1). "Watch the drawn scene … gain segments" at 0.3 does not occur (M2P-m3).

**Learner experience.** The prose is accurate and unusually explicit about what each number means and does not mean,
and every principal cell says what to look for in its output. But a learner new to panoptic segmentation meets no
roadmap, no prediction prompts, no checkpoint questions with sample answers, no guided experiment, no troubleshooting
and no conclusion prompt, and has to scroll past 1,256 lines of carried package code that nothing tells them they can
skip (M2P-M2).

**Spec conformance.** Unresolved applicable `MUST`s: RUN1, RUN10, ENV6, REL2, REL11 (M2P-M1); DAT19 (M2P-m1); VAL7
(M2P-m2); REL12 (BYOD never verified, M2P-m4). `SHOULD` deviations not durably recorded: GDL1–GDL14, UX5 (M2P-M2,
M2P-m3); EXE2 (M2P-m1); EXE5 (M2P-m5); EVAL10 (M2P-S1).

## 3. Findings

### M2P-M1 — Major: Run all stops at the install cell; the only clean-runtime run needed a restart

- **Cell/section:** Section 1, cell 3 (generator: `tools/build_notebook.py:61–72` install-cell template; Section 1
  prose at `tools/build_notebook.py:487`).
- **Observed issue:** The cell pip-installs `torch==2.14.0`, `numpy==2.5.3` and six other pins into the running kernel,
  then raises `RuntimeError(... Restart the runtime, then rerun from the top.)` when an already-imported distribution
  changed. On the recorded hosted image it did exactly that. The opening cell nevertheless promises that the default
  path "needs no … configuration edit" and no intervention, and `tutorials/README.md` lists Run-all as "verified —
  clean-runtime `Run all` execution recorded … 10/10 code cells".
- **Consequence:** A learner choosing Run all in a fresh hosted runtime stops at the first code cell and must restart
  and re-run by hand; the registry's "verified" wording hides that.
- **Evidence:** Documented execution evidence, exact blob: Kaggle `run_summary.json` pass 1 `ok: false` with
  `numpy: loaded=2.0.2, installed=2.5.3`; pass 2 ok after `restarted_after_install_cell: true`;
  `docs/release-verification.md` records "1 restart after the install cell" under **PASSED**. Source inspection of
  cell 3. Colab: not verified (no record), but Colab's preloaded NumPy differs from the 2.5.3 pin in the same way.
- **Recommended correction:** Replace the in-kernel install with the fleet's uv isolated-environment pattern: a carrier
  cell bootstraps uv, creates `uv venv --managed-python --python 3.12.12 <ROOT>/env`, installs a hash-locked
  `requirements.txt` with `uv pip install --require-hashes --only-binary :all:`, and runs the workload in that
  environment so the kernel's preloaded NumPy/torch are never replaced (reference:
  `ast-audio-classification-pipeline/tutorials/DIMER_Sound_Event_Classification_Workshop.ipynb` on `origin/main`).
  Change it in the generator, not the notebook. Until a one-pass run is recorded, reword the `tutorials/README.md`
  Run-all column and the release-verification "PASSED" rows to say the run was restart-assisted.
- **Acceptance check:** A fresh hosted runtime (Colab, or the Kaggle image above) executes every code cell of the new
  blob in order in one kernel with no error output and no restart, recorded with blob, runtime and outcome in
  `docs/release-verification.md`; `tutorials/README.md`, README.md and STATUS.md agree with that record.
- **Spec:** RUN1, RUN10, ENV6, REL2, REL11.

### M2P-m1 — Minor: BYOD upload failures are raw exceptions, and BYOD has no location field

- **Cell/section:** Section 4, cell 11 BYOD branch (`tools/notebook_template.py:114–123`).
- **Observed issue:** A non-image upload raises `UnidentifiedImageError: cannot identify image file <_io.BytesIO …>`;
  a cancelled upload raises a bare `StopIteration` from `next(iter(uploaded))`. Neither names the contract or the next
  step. The branch can only read through `files.upload()`; there is no path field, so it cannot run outside Colab or
  under an executor.
- **Consequence:** A learner who picks the wrong file or cancels gets a traceback instead of "upload one PNG/JPEG/WebP
  image, 16–4096 px per side"; BYOD cannot be verified non-interactively.
- **Evidence:** Direct execution P04 (d), (e); P04 (c) shows the size rejection is already actionable. Source
  inspection.
- **Recommended correction:** Add `BYOD_IMAGE_PATH = ''  # @param {type:"string"}` read in preference to the upload
  dialog; wrap the upload and decode so an empty upload and an undecodable file raise a `ValueError` naming the
  accepted formats, the side limits and "set USE_BYOD = True and re-run from this cell".
- **Acceptance check:** With the upload stubbed to `{}` and to a text file, cell 11 raises one-line errors naming the
  failed condition and the corrective action; with `BYOD_IMAGE_PATH` set to a JPEG, cells 11–21 complete without
  importing `google.colab`.
- **Spec:** DAT19, UX10, EXE2.

### M2P-m2 — Minor: BYOD silently alters some valid images (EXIF orientation, 16-bit modes)

- **Cell/section:** Section 4 cell 11 and the carried `validate_image` (`src/mask2former_panoptic_pipeline/pipeline.py:154–162`).
- **Observed issue:** The input contract accepts "any mode, converted to RGB". A phone JPEG with an EXIF orientation
  tag is segmented and exported in sensor orientation without a word (P04 a: 480 × 640, one segment fewer and lower
  scores than upright). A 16-bit greyscale PNG is clipped by `convert("RGB")` to two values, so the model sees an
  almost blank image and labels it `sky-other-merged` over 100 % with a `not-measurable` report and no warning (P04 b).
- **Consequence:** A learner's own photograph can produce a confidently wrong or sideways map with nothing in the
  manifest saying the input was altered.
- **Evidence:** Direct execution P04 (a), (b); source inspection of `validate_image`.
- **Recommended correction:** Apply `ImageOps.exif_transpose` before validation and record the applied orientation in
  the input manifest; reject (or explicitly rescale and report) modes `I`, `I;16*` and `F`; state both rules in the
  Prerequisites BYOD paragraph.
- **Acceptance check:** The P04 (a) upload is segmented at 640 × 480 and the manifest records the transpose; the P04 (b)
  upload is either rejected with a message naming the mode or rescaled with the rescale recorded in the manifest.
- **Spec:** VAL7, DAT12.

### M2P-m3 — Minor: The "Next experiments" have no rerun instruction, and one stated outcome does not occur

- **Spec:** GDL7, GDL8, GDL10, UX5.

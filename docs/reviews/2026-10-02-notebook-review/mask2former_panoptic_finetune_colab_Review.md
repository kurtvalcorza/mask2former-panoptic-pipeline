## Executive assessment

The default adaptation path is technically sound and honestly framed. The pinned base weights are digest-verified
before loading; the dataset is validated into a manifest with a recorded rejection; the split precedes any weight
change; the re-headed baseline and a trivial baseline are measured before training; the fine-tune states what is
frozen, labels its loss as optimisation evidence only and records its hyperparameters; held-out PQ is computed through
the inference path; and the exported artifact reloads from disk with an identical score and pixel-identical map, while a
tampered manifest is refused. The exact blob under review has a clean-runtime Kaggle T4 record, and a direct CPU
execution in this review reproduced the CPU smoke numbers exactly (54 steps, mean epoch loss 33.75 → 6.76, held-out PQ
0.866, per class `box` 0.509, new-seed PQ 0.952).

Three Major problems stop it being ready. **Run all does not complete in one pass**: the Kaggle T4 record shows the
install cell raising its own restart guard (`cuda-bindings: loaded=12.9.4, installed=13.4.2; numpy: loaded=2.0.2,
installed=2.5.3`) and passing only after the executor restarted the kernel. **The declared `GUIDED` layer is largely
absent**, and 1,256 lines of carried package code are not marked as infrastructure. **The documented experiments
silently produce the wrong experiment**: following "set `EPOCHS` to 2 and watch PQ fall" in the natural way (edit the
form in Section 5, re-run it, then the fine-tune and evaluation cells) continues training the already-adapted model, so
held-out PQ *rises* from 0.866 to 0.963 while the run record claims 2 epochs and 18 steps; the experiment only works if
the learner also re-runs the re-head cell, which nothing says. Six Minor findings cover BYOD recovery messages, BYOD
promises the branch does not keep, an understated trivial baseline, hard-coded CPU numbers and unexplained warnings,
evidence gaps, and an undocumented environment variable.

No finding here says the recorded default-path numbers are wrong.

## 2. Separate judgments

**Technical correctness.** Strong on the default path: identity asserted twice, digest verification before load, no
remote code, validation through the same ceilings `finetune` applies, split before training, artifact manifest with
digests, exact reload and tamper refusal. Defects: the in-kernel install cannot complete Run all in one pass on the
recorded hosted image (M2F-M1); `finetune` on an already-adapted pipeline silently continues training and records only
the latest call's epochs and steps, so a documented experiment and the exported training record go wrong (M2F-M3).

**Scientific validity.** Split discipline, single-use holdout and the sample-metric framing are correct, and the loss
is never presented as task evidence. The trivial baseline chosen is the weakest available one; a two-band predictor
already scores 0.318, so the "number any adapted model must clear" is understated and the stuff PQ of 0.999 is less
informative than the prose implies (M2F-m3). Hard-coded CPU per-class numbers and an unverified causal explanation for
`box` are presented as what the learner will see (M2F-m4).

**Promise fulfilment.** The default promises are delivered and evidenced by the exact-blob Kaggle run and this review's
CPU run, except "no … intervention" (M2F-M1). "Watch PQ fall" holds only under an undocumented rerun order (M2F-M3).
The BYOD dataset branch reaches every stage it lists except the promised trivial baseline, and writes no manifest or
report for the learner's own run (M2F-m2).

**Learner experience.** The prose explains each stage accurately and repeatedly says what each number does and does
not mean. But there is no audience statement, roadmap, glossary, prediction prompt, checkpoint with sample answer,
structured experiment, troubleshooting or conclusion prompt, and the 1,256 lines of carried code are not marked as
skippable (M2F-M2). Several warnings appear in the outputs that the text never explains (M2F-m4).

**Spec conformance.** Unresolved applicable `MUST`s: RUN1, RUN10, ENV6, REL2, REL11 (M2F-M1); FT6, SRC2 (M2F-M3);
DAT19 (M2F-m1); REL12 (BYOD never verified, M2F-m5). `SHOULD` deviations not durably recorded: GDL1–GDL14, UX5, UX8
(M2F-M2); GDL10 (M2F-M3); EXE2, UX10 (M2F-m1); EVAL10 (M2F-m2, M2F-m3); GDL8 (M2F-m4); EXE5 (M2F-m6).

## 3. Findings

### M2F-M1 — Major: Run all stops at the install cell; the only clean-runtime run needed a restart

- **Cell/section:** Section 1, cell 3 (generator: `tools/build_notebook.py:51–72` install-cell template, `:511` the
  skip switch).
- **Observed issue:** The cell pip-installs `torch==2.14.0`, `numpy==2.5.3` and six other pins into the running kernel,
  then raises `RuntimeError(... Restart the runtime, then rerun from the top.)` when an already-imported distribution
  changed. On the recorded hosted T4 image it did exactly that (two distributions: `cuda-bindings`, `numpy`). The
  opening cell nevertheless promises Run all with "no configuration edit" and no intervention, and
  `tutorials/README.md` lists Run-all as "verified — clean-runtime `Run all` execution recorded … 13/13 code cells".
- **Consequence:** A learner choosing Run all in a fresh hosted runtime stops at the first code cell and must restart
  and re-run by hand; the registry's "verified" wording hides that.
- **Evidence:** Documented execution evidence, exact blob: Kaggle `run_summary.json` pass 1 `ok: false` with the
  message above; pass 2 ok after `restarted_after_install_cell: true`; `docs/release-verification.md` records "1
  restart after the install cell" under **PASSED**. Source inspection of cell 3. Colab: not verified (no record).
- **Recommended correction:** Replace the in-kernel install with the fleet's uv isolated-environment pattern: a carrier
  cell bootstraps uv, creates `uv venv --managed-python --python 3.12.12 <ROOT>/env`, installs a hash-locked
  `requirements.txt` with `uv pip install --require-hashes --only-binary :all:`, and runs the workload in that
  environment so the kernel's preloaded NumPy/torch are never replaced (reference:
  `bioclip2-biodiversity-pipeline/tutorials/DIMER_Philippine_Biodiversity_Field_Survey_Capstone.ipynb` on
  `origin/main`). Change it in the generator, shared with the `TASK-INFERENCE` notebook (M2P-M1). Until a one-pass run
  is recorded, reword the `tutorials/README.md` Run-all column and the "PASSED" rows to say the run was
  restart-assisted.
- **Acceptance check:** A fresh hosted runtime (Colab, or the Kaggle T4 image above) executes every code cell of the new
  blob in order in one kernel with no error output and no restart, recorded with blob, runtime and outcome in
  `docs/release-verification.md`; `tutorials/README.md`, README.md and STATUS.md agree with that record.
- **Spec:** RUN1, RUN10, ENV6, REL2, REL11.

### M2F-M3 — Major: The documented experiments silently stack training on the already-adapted model and mislabel the run

- **Cell/section:** Closing cell 28 "Next experiments" (`tools/notebook_template_finetune.py:456–459`); the form layout
  of cells 13 (`EPOCHS`) and 17 (`FREEZE_BACKBONE`, `LEARNING_RATE`, `BATCH_SIZE`); the carried

- **Observed issue:** The closing cell says "set `EPOCHS` to 2 and watch PQ fall; … set `FREEZE_BACKBONE = False` and
  compare" without saying which cells to re-run. `EPOCHS` sits in the Section 5 data cell, the re-head is in Section 6,

  path (fewer epochs "improve" the model), and the artifact's provenance can misstate how the weights were produced.
- **Evidence:** Direct execution P03 (a) vs (b) on the review CPU; source inspection of `finetune` (no `self.adapted`
  guard, local `step` counter).
